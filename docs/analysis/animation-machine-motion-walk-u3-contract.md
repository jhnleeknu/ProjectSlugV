# `480bc` 프레임 helper 묶음 U3: motion walk 계약

**상태: 메인 리뷰를 거쳐 확정(아래 메인 결정). 구현·검증 기록이 아니다.** 범위 근거는 `animation-machine-480bc-scope.md`의 U3, 진입 경계는 확정된 U2 계약(`animation-machine-scene-core-u2-contract.md`, 선택 A)의 비null motion 분기 대상 `19812`/`19844`/`19910`이다. Claude Opus 5.5 / high 분석 작업자가 canonical BE ROM(SHA256 `29112a94b5c073de95919ab4efbc75427287739eab794ef442d2aa7c886c860f`, `extracted/program/maincpu.decrypted.be.bin`, fixed CPU 주소=file offset)을 capstone M68000으로 디코드하고 기존 관측 산출물을 읽기 전용으로 재생해 작성했다. [F]=원본 바이트 또는 기록된 산출물에서 확인한 사실, [I]=추론, [U]=미확인. 명령 단위 정답은 원본 바이트 자체다. 같은 루틴들의 typed host 재구성(`engine/src/scene_motion.cpp`, 문서 `scene-motion-evaluation.md`·`scene-motion-time.md`·`scene-motion-pair.md`·`scene-motion-bounds.md`)은 machine 실행부가 아니며 교차 확인 자료로만 쓴다.

메인 결정(Claude Opus 5.5, 원본 대조 리뷰 후): (1) 처리 범위는 선택 F(36 type slot 전부, block 시작 370)로 확정한다. (2) carry: 68000의 TST/AND는 항상 C=0이므로 `19710`/`1971c`의 TST.W, `19372`/`1957a`의 AND.W block은 known Clear를 남긴다. 이 known Clear 지정은 위 소비 block으로 이어지는 생산 block에 한정하며, 검증기의 source 분류도 이 PC들에서 같은 규칙을 쓴다(그 밖의 MOVE/TST/AND block은 기존처럼 Unknown). (3) 범위 밖 type은 U2 정책처럼 계산된 PC로 그대로 이동한다(지원 block 시작이면 실행, 아니면 기존 unsupported/홀수 PC 오류).

## 메인 결정 항목(위에서 확정)

1. **Handler 범위**(아래 "handler 범위 선택"): 선택 F(36 slot 전부, block 시작 370) 또는 선택 S(37 추출 경로에 있는 11 type만, block 시작 170, 나머지는 `unsupported animation machine PC` rollback). 작업자 권고는 F다.
2. **계산된 known Clear**: `19710`·`1971c`(TST.W)와 `19372`·`1957a`(AND.W) block은 68000 정의상 C=0이다. carry 소비 block 6개가 이 값에 의존하므로 U2의 `1a2e0`(CMP+EORI) 선례처럼 known Clear로 계산하자고 제안한다. 기존 verifier의 opcode 분류(`classify_carry`: ORI/ANDI만 known)는 TST/AND를 Clear로 확장해야 한다.

## 실행 의미(A5=`108000` 기준 절대 주소)

[F] 모든 RAM 접근은 A5 상대 d16이다: `53b4`→`10d3b4`(motion cursor LONG), `53b8`/`53ba`→`10d3b8`/`10d3ba`(기준 X/Y WORD), `53bc`/`53c0`→`10d3bc`/`10d3c0`(현재 X/Y LONG), `53c4`/`53c8`→`10d3c4`/`10d3c8`(제안 X/Y LONG). 구현은 live A5로 계산한다. ASR은 산술(부호 채움), LSL은 0 채움이다. 추가 사실: Scc.B(SLT/SGT)는 하위 BYTE만 `ff`/`00`으로 쓰고 flag를 바꾸지 않는다. EXT.W는 하위 BYTE를 하위 WORD로 부호확장하고 상위 WORD를 보존한다. SUBQ.L #1은 LONG 빌림, SUBQ.W/ADDQ.W #1은 WORD wrap이다. MOVEM.L은 flag를 바꾸지 않는다(`-(A7)` mask `0300`=D6,D7; `(A7)+` mask `00c0`=D6,D7). 조건 분기: BCS/BCC=C, BEQ/BNE=Z, BMI/BPL=**N만**(CMP 뒤에도 V 무시), BLE=Z|(N^V), SLT=N^V, SGT=¬Z∧¬(N^V).

## Handler 범위 선택(메인 결정 1)

- [F] 원본 dispatcher 5개는 type 범위를 검사하지 않는다. JMP 대상은 `표 시작+sext(D4.W)`다.
- 선택 F(36 slot): block 시작 370, 바이트 3156. 범위 밖 type은 U2 조건 index 정책과 같이 계산된 PC를 그대로 따른다. 그 PC가 block 시작이면 실행하고(예: type `90`은 다섯 dispatcher 모두에서 첫 handler·꼬리 PC인 `18c9e 18d42 18f92 1906a 1935c`로 간다), 아니면 `unsupported animation machine PC`, 홀수(예: 종료 type `ffff`→표 시작−1)는 기존 홀수 PC 오류로 전체 rollback한다.
- 선택 S(11 type `04 08 0c 10 14 20 24 40 48 64 80`): block 시작 170. 목록 밖 type의 slot PC는 block 시작이 아니므로 같은 `unsupported animation machine PC` rollback이 guard가 된다(전용 코드 불필요). 선택 S에서도 type `90`은 `18c9e`·`18f92`·`1935c`처럼 우연히 block 시작인 PC에서는 실행되고 `18d42`·`1906a`에서는 거부된다.
- 작업자 권고: **선택 F.** 근거: (1) [F] 자연 seed의 U3 구간에서 실제로 나온 type은 `14 40 64 80` 4종뿐이라 선택 S도 7종은 합성 RAM 경로로만 검증할 수 있다. 검증 부담 차이는 type 수에 비례할 뿐 방식은 같다. (2) [F] 36 handler는 표에서 기계적으로 나오는 규칙적인 코드(추가 200 block 중 125는 BRA 하나짜리 slot)이며 기존 typed 구현이 36 type 합성 비교를 이미 통과했다(`scene-motion-evaluation.md` 합성 6,704, `scene-motion-pair.md` 1,846). (3) [U] 37 경로는 script opcode 0 operand 정적 수집 결과라 runtime `10d3b4`의 모든 값을 포괄한다는 증거가 없다. (4) [F] `18c06`·`18caa`·`18fd2`·`1972a`는 U3 밖 호출자 `19938`(`1a692`), `19768`(`1a626`), `19772`(`1a17e`)도 쓰며, stage_entry_body trace에서 `19938` 경유 type `0c`·`24`가 실제 실행됐다(`18c1a 18c32 18cbe 18cd6 18fe6 18ffe`).
