# IRQ 신호 생산과 메인 프레임 대기 연결

원본 프로그램 SHA256: `29112a94b5c073de95919ab4efbc75427287739eab794ef442d2aa7c886c860f`.
`tools/verify_interrupt_frame_flow.py`는 기존 C++ `begin_interrupt_service`와 `poll_input_control`을 같은 RAM 상태로 비교한다. 새 시간축이나 별도 카운터 근사 모델을 도입하지 않는다.

## 연결 방식

원본 메인 CPU를 ef2에서 실행하여 대기 또는 입력/컨트롤러 경계까지 진행한다. 대기 중에는 CPU 문맥을 보관하고 별도 외부 스택에서 실제 c8c를 실행한다. 완료 후 메인 문맥을 복구하되 c8c가 바꾼 RAM은 유지한다. C++에서는 같은 RAM을 IRQ 서비스와 메인 poll에 차례로 제공한다.

이 문맥 복구는 별도 검증한 IRQ envelope의 레지스터 보존에 근거한 **명시적 호스트 스케줄링 조건**이다. 하드웨어 예외 주입·SR/RTE·BIOS나 실제 시간 간격을 실행한 것은 아니다. IRQ 서비스는 렌더링 비활성, 사운드 타이머0 및 유효한 빈 큐 조건을 사용한다. 렌더링 비활성 분기가 잘못된/비어 있지 않은 작업 포인터도 조회하지 않는 것을 포함한다.

RAM100016은 각 시나리오 시작의0 또는254 외에는 호스트가 수정하지 않는다. 실제 c8c의 포화 증가와 실제 f12의 신호 소비만 이 값을 변경한다. ef2가 대기할 때는 비디오·입력을 읽지 않는다. 준비되면 비디오를 한 번 읽고 f12에서 기존 신호를10001a로 옮기고100016을0으로 지운 뒤 입력 갱신을 실행한다.

연속 프레임은 RAM을 승계하지만 각각의 다음 poll 진입 레지스터는 명시적으로 설정한다. 앞선ec4 코드와 사용자 콜백 본문까지 자동으로 이어 실행한 전체 메인 루프라는 뜻은 아니다. 대기 중 IRQ 전후의 D1/A6 및 모든 메인 레지스터 보존은 실제 문맥을 비교한다.

## 검증 결과

```sh
.venv/bin/python tools/verify_interrupt_frame_flow.py
```

573조건: IRQ 서비스279회, 메인 poll294회(대기280/준비14)와 순서 있는 포트1,070개가 일치했다. 전체 RAM, 비디오·입력·사운드 읽기 횟수, 반환 경계 및 포트 순서를 비교했다. 실제 MS5D/MS5P 런타임 파일과 원본 payload의 일치도 검사한다.

- 임계값0/1/2/3/255, 연속 프레임과 다양한 비디오/입력 샘플.
- 0에서 원본 IRQ 서비스255회로255 도달, 별도254→255 이후 추가 서비스의 포화 유지.
- 재진입 guard3조건에서 신호가 증가하지 않아 대기 유지.
- f3c 콜백 경계10회, ec4 컨트롤러 반복 경계3회, 정상 반환1회.
