# 작업·이전·다중 컴퓨터 개발 절차

## 현재 범위

2026-10-14 기준 이 문서는 향후 실행할 절차를 기록한다. 현재 기준은 로컬 `codex/f4-f5-acceptance`의 `3d7d11a`, 엔진 인수 기준은 `b8502bf`다. 최근 F4/F5 인수는 완료했지만 전체 게임은 미완료이며, 전체 완료 판단은 `docs/GOAL.md`를 따른다. 이 계획 기록만으로 삭제·원격 설정·게시를 실행하지 않는다.

GitHub 이전 목적지는 `https://github.com/jhnleeknu/ProjectSlugV.git`이다. 게시할 기준 브랜치는 실행 시 명시적으로 확인한다. 아직 정하지 않은 기본 브랜치를 `main`으로 가정하지 않는다. 새 원격 저장소나 공개 범위를 임의로 만들거나 변경하지 않는다.

사용자가 요구한 빈 README는 저장소 루트 `README.md`에 적용한다. 새로 만들 때 0바이트로 유지하며, 기존 루트 파일이 있다면 이전 실행 시 요구사항과 상태를 확인한다. 기존 `engine/README.md`와 규격·분석 문서는 유지한다. 이번 계획 기록에서는 README를 생성하지 않는다.

## 역할과 작업 계약

- Codex와 Claude 작업 모두 서브에이전트 사용을 필수 운영 원칙으로 한다. 메인은 원본 의미의 심화 추론, 설계·규격 확정, 최종 리뷰·통합을 담당하고, 작업자는 확정된 사양의 실제 코딩·검증·문서화를 분산 수행한다. 새 해석이 필요하면 근거와 질문을 메인에 반환한다.
- 모델·effort와 역할은 `AGENTS.md`를 따른다. 내부 작업자는 `gpt-6.1-sol / medium`, Claude 일반 구현은 `claude-sonnet-5-5 / medium`, 어려운 구현·독립 검토는 `claude-opus-5-5 / high`를 명시한다. 실제 사용 가능 여부와 적용 모델·effort를 실행 기록에 남기며, 요청과 다르면 보고한다.
- 작업자 상한은 메인 제외 전체 5개, 내부 Sol 최대 3개다. 외부 Claude와 그 하위 작업도 전체 상한에 포함하고 중첩 위임으로 우회하지 않는다. 독립 작업이 충분하면 3~4개를 운용한다. 실행 실패·사용량 제한 시 허용된 다른 작업자로 재배정하고, 대체가 불가능하면 메인 수행 사유를 기록한다.
- 위임마다 입력·기준 커밋·산출물·담당 파일·공통 규격·검증 기준을 명시한다. 작업자별 브랜치·worktree·빌드·출력 경로를 정하고 같은 파일을 동시에 수정하지 않는다. Claude에도 `AGENTS.md`와 `docs/GOAL.md`의 관련 규칙을 전달한다.
- 메인은 실제 diff, 원본 근거, 검증 결과를 확인한 뒤 결과를 수용한다. 진행 보고에는 실행 중인 작업자의 모델·effort·담당 작업과 배정이 적은 이유를 기록한다.

## 완료 후 정리와 GitHub 이전 순서

1. **`artifacts` 정리:** 삭제 전 목록과 용도를 확인하고 재생성 명령·입력 해시·도구 버전·출력 위치를 기록한다. `0258` 인수 manifest가 참조하는 ignored `artifacts` 보고서와 `build/legacy_acceptance`의 로그·receipt·실패 inventory까지 연결해 보존한다. 참조 파일을 이동하면 원래 manifest는 보존하고 별도 이전 목록에 원래 경로·새 경로·동일 파일 해시를 기록한다. 경로 이동을 새 검증 성공으로 취급하거나 역사적 pin을 덮어쓰지 않는다. 오래된 재생성 가능한 중간 산출물만 정리한다. 최종 결과와 검증 근거는 보존하며, ROM·추출 게임 데이터는 Git에 넣지 않는다. Git에 못 넣는 보존 결과는 별도 보관 위치와 해시로 인수인계한다. 근거가 그 파일에만 있거나 재생성을 확인하지 못한 항목은 보류한다.
2. **완료된 `claude-integration` 작업 복사본 정리:** 일반 복사본인지 Git worktree인지 먼저 구분하고 각 branch/HEAD, 변경·미추적 파일, ignored 필수 결과, 미반영 커밋과 결과 폴더를 조사한다. `git status`에 나타나지 않는 ignored 필수 산출물은 별도 목록으로 확인한다. 코드가 통합본에 반영되고 필요한 결과·검증 근거가 본 폴더에 반영되었는지 확인한다. 미반영 항목을 먼저 회수·리뷰·검증하고 보존 위치를 기록한 뒤 완료된 복사본을 정리한다. `.venv`·`extracted`·`artifacts` 등의 링크가 가리키는 원본과 사용 중인 다른 checkout을 확인하고 공유 원본은 삭제하지 않는다. 재귀 정리가 심볼릭 링크를 따라가게 하지 않는다. 등록된 worktree는 해당 관리 도구로 제거한다. 이름이 같거나 작업자 완료 보고가 있다는 이유만으로 삭제하지 않는다.
3. **GitHub 게시:** 앞의 두 단계 완료와 보존 기록을 확인한 뒤 목적지·접근 권한·원격 이력·게시 기준 브랜치를 확인한다. 기존 remote가 있으면 URL과 용도를 먼저 확인한다. tracked 파일과 게시할 전체 이력을 점검하여 ROM·추출 데이터·비밀정보가 없는지 확인하고, 발견 시 게시를 중단하여 해결한다. 검증·메인 리뷰·문서 갱신을 마친 커밋을 명시된 브랜치로 push한다. 이후 변경은 PR에 근거·검증·제약을 기록하고 채팅에 연결하며 원격 병합은 사용자 지시를 따른다.

삭제 대상·보존 위치·대상 커밋·검증 결과는 `docs/STATUS.md`와 `docs/reviews/`에 남긴다. 이 순서는 F4/F5 같은 부분 인수만으로 전체 완료를 선언하거나 기존 완료 작업을 반복하는 근거가 아니다.

## 각 컴퓨터에서 작업 시작

GitHub 이전 이후 공유 소스·규격·분석·리뷰 기록의 기준은 GitHub에 게시된 커밋이다. 컴퓨터 간 로컬 폴더 복사로 소스 기준을 교체하지 않는다.

새 컴퓨터에는 `git clone https://github.com/jhnleeknu/ProjectSlugV.git <새작업폴더>`로 받아 시작한다. 아래 `origin`은 지정 URL과 대조한 실제 remote를 뜻하며, 이름이 다르면 그 이름을 사용한다. Codex·Claude의 주 에이전트도 시작할 때 `AGENTS.md`, `docs/GOAL.md`, `docs/STATUS.md`, 이 문서를 명시적으로 읽는다. 도구가 자동으로 모든 규칙 파일을 불러온다고 가정하지 않는다. 계획 작업도 담당 범위·기준 커밋·진행 중인 담당자를 상태 기록에서 확인하고 중복 착수를 피한다.

1. `git status --short`, `git branch -vv`, `git remote -v`로 위치·브랜치·upstream·변경을 확인한다. 미완료 변경이 있으면 내용과 소유자를 확인하고 체크포인트로 보존한다. 다른 작업자의 변경을 버리거나 덮어쓰지 않는다. 작업 시작은 변경이 정리된 상태에서 한다.
2. 원격을 확인한 후 `git fetch origin`으로 최신 이력을 가져온다. 인수인계에 명시된 기준 브랜치와 커밋을 확인하고 그 브랜치를 checkout한다. 처음 받는 브랜치는 실제 존재를 확인한 뒤 `git switch --track origin/<기준브랜치>`로 추적한다. 기존 브랜치는 upstream이 의도한 원격 브랜치인지 확인한다.
3. `git pull --ff-only`로 갱신한다. 실패하면 로컬·원격 이력 차이를 조사하고 해결 후 진행한다. 임의 reset이나 force로 맞추지 않는다.
4. 확정된 기준 커밋에서 `codex/<작업명>` 같은 작업 브랜치와 작업자별 worktree를 만든다. 두 컴퓨터가 같은 작업 브랜치를 동시에 갱신해야 한다면 소유권을 먼저 넘기며, 보통 컴퓨터·작업자별 브랜치를 사용한다.

## 환경과 경로 재현

- `.venv`, ROM, 런타임 리소스와 ignored 출력은 Git으로 전달되지 않는다. 가상환경은 각 컴퓨터에서 다시 만들고, ROM은 별도 확보 후 기존 해시와 일치하는지 확인한다. 런타임 리소스·중간 출력은 버전 관리된 도구와 기록된 명령으로 재생성하고 C++ 로더 검증까지 수행한다.
- 필요한 Python·컴파일러·빌드 도구 버전과 의존성 pin을 확인한다. 현재 스크립트·문서·설정의 절대 경로 의존점을 점검하고, 저장소 상대 경로 또는 명시적 입력 옵션으로 이동성을 확보한다. 로컬 ROM 경로·출력 경로는 인수인계에 명시하되 기계별 설정으로 관리한다.
- 플랫폼·기계별 pin이나 라이브러리 차이를 무시하거나 검증 실패를 성공으로 처리하지 않는다. 차이, 실제 적용 버전, 영향과 재검증 결과를 기록한다. 공통 pin 변경이 필요하면 별도 리뷰한다.

## 작업 종료·인수인계·충돌 처리

1. 변경 범위에 맞는 빌드·재생성·원본 비교·회귀 검증을 실행한다. 실패·미확인은 해결하거나 명시한다. 메인 리뷰에서 발견한 문제를 수정하고 필요한 검증을 다시 수행한다.
2. `docs/STATUS.md`에 완료 범위, 원본 근거, 검증 명령·결과, 미해결 사항, 다음 작업을 남기고 `docs/reviews/`에 대상 커밋과 리뷰 결과를 기록한다. 검토 가능한 크기로 커밋하며 ROM·추출 데이터는 stage하지 않는다. 현재 `.venv`와 `extracted`는 symlink여서 디렉터리용 ignore 패턴에도 미추적 항목으로 표시된다. `git add -A`로 일괄 stage하지 않고 승인된 소스·문서 경로를 명시적으로 stage한다. `git diff --cached`와 게시할 이력에서 symlink·추출물 포함 여부를 검사한다.
3. 다른 컴퓨터로 넘기는 미완료 작업도 명확한 체크포인트 커밋으로 보존한다. 작업 브랜치·HEAD·미완료 범위·실행 중인 작업자·환경·별도 보존 결과·다음 명령을 기록한다. 체크포인트나 부분 검증을 전체 인수 완료로 표시하지 않는다.
4. push 직전 다시 fetch하여 원격 변화를 확인한다. non-fast-forward 거절 또는 충돌이 생기면 원격 변경과 소유자를 확인하고 정상 merge 등으로 해결한다. 충돌 해결 후 영향받는 검증과 리뷰를 다시 수행하고 push한다. 최초 작업 브랜치는 `git push -u origin HEAD`, 추적 설정 후에는 `git push`를 사용한다. 게시된 브랜치의 원격 HEAD가 전송할 로컬 커밋과 같은지 확인하고 브랜치·커밋·게시 상태를 인수인계에 기록한다. 네트워크 실패로 미푸시인 커밋은 다른 컴퓨터에서 받을 수 있다고 표시하지 않는다. `--force`·`--force-with-lease`로 공유 이력을 덮어쓰지 않는다.
5. 다음 컴퓨터는 게시된 체크포인트를 fetch하고 커밋·상태 기록을 확인한 뒤 시작한다. 원격이 없는 단계에서는 로컬 브랜치·diff·리뷰 기록과 별도 보존 위치로 인수인계하고 로컬 커밋을 PR이라고 부르지 않는다.
